# L1 分支并行扩展 与 上市公司过滤

记录日期：2026-07-30

本文记录两件事的实现方式：
1. **构建侧**——把一级分支扩展从串行改成并行；
2. **展示与导出侧**——如何从全量挂载结果中抽取上市公司。

两者互不相关，但都属于"同一份数据、换一种取用方式"的思路：并行不改变产出内容，上市过滤不改变挂载关系。

---

## 一、L1 分支并行扩展

### 1.1 原来的问题

分阶段构建的第三步是逐个扩展一级分支。原实现是一个朴素的 `for` 循环，每轮串行完成"调百炼扩展 → 命名空间化 → 校验 → 质量评估 → 未通过则修正 → 再校验"。

瓶颈完全在网络等待上：每个分支要发 1–3 次百炼 Responses 请求（扩展 + 评估 + 可能的修正），每次都带 `web_search`、超时上限 600 秒。一个有 8 个 L1 的行业，串行跑下来是纯粹的等待叠加。

### 1.2 为什么可以直接并行

改之前确认了三个前提：

| 前提 | 依据 |
|---|---|
| 分支之间无数据依赖 | 每个分支只读 `seed_graph` / `seed_blueprint` / 自己的 `branch_node`，不读其他分支的产出 |
| 无 ID 冲突 | `namespace_branch_graph` 把节点 ID 重写为 `{branch_id}_001` 起的分支专属前缀，命名空间由分支自身唯一确定 |
| 客户端线程安全 | `call_bailian_responses` 每次调用内部 `new` 一个 `OpenAI` client，不共享连接状态 |

另外 `namespace_branch_graph` 内部 `deepcopy`，评估器只读 `seed_graph`，没有共享可变状态。

### 1.3 改动清单

| 文件 | 改动 |
|---|---|
| `tools/agent/build_candidate_graph.py` | 抽出 `_expand_one_branch()`；串行循环换成 `ThreadPoolExecutor` |
| `tools/agent/search/staged_bailian_builder.py` | 新增 `staged_branch_concurrency()`；`_env_int()` 补 `load_bailian_env()` |
| `README.md` / `AGENTS.md` | 补并发参数说明 |

### 1.4 第一步：把循环体抽成纯函数

`_expand_one_branch()`（[build_candidate_graph.py:280](../tools/agent/build_candidate_graph.py)）原样搬入了循环体的全部逻辑，只改了两点：

- 只读入参，不写任何外层变量；
- 失败时**返回**一条 `status="failed"` 的记录，而不是往外层 list 里 append。

```python
    except Exception as exc:
        _log(f"分支 {branch_name} 扩展或评估失败，已记录后继续其他分支。")
        return {
            "branch_id": branch_node.get("id"),
            "branch_name": branch_name,
            "status": "failed",
            "error": f"{type(exc).__name__}: {exc}",
        }
```

这一步是并行的前提：函数没有副作用，才能安全地丢进线程池。

### 1.5 第二步：线程池 + 顺序回填

```python
    branches_to_expand = level_one_nodes[:branch_limit]
    max_workers = staged_branch_concurrency(len(branches_to_expand))
    _log(f"并行扩展一级分支，最大并发 {max_workers}；分支之间互不依赖，日志可能交叉输出。")

    records_by_index: dict[int, dict[str, Any]] = {}
    if branches_to_expand:
        with concurrent.futures.ThreadPoolExecutor(max_workers=max_workers) as executor:
            futures = {
                executor.submit(_expand_one_branch, industry_id, resolved_industry_name,
                                target_depth, seed_graph, seed_blueprint,
                                branch_node, index, len(branches_to_expand)): index
                for index, branch_node in enumerate(branches_to_expand, start=1)
            }
            for completed, future in enumerate(concurrent.futures.as_completed(futures), start=1):
                records_by_index[futures[future]] = future.result()
                _log(f"分支进度 {completed}/{len(branches_to_expand)}。")

    # 按一级骨架顺序回填，保证产物与串行实现完全一致。
    branch_records = [records_by_index[index] for index in range(1, len(branches_to_expand) + 1)]
    branch_graphs = [r["graph"] for r in branch_records if r.get("status") == "ok"]
    staged_errors = [
        {"branch_id": r.get("branch_id"), "branch_name": r.get("branch_name"), "error": r.get("error")}
        for r in branch_records if r.get("status") != "ok"
    ]
```

**两个关键设计：**

- **顺序回填**。`as_completed` 是按完成先后返回的，直接 append 会让 `staged_branch_evaluations.json` 里的分支顺序每次运行都不同，diff 无法阅读。所以用 `futures[future]` 取回原始下标，按 index 重排成 list。
- **错误语义不变**。单分支失败仍不中断其他分支，全部跑完后照旧汇总抛 `RuntimeError`，并保留分支产物、不生成校验前候选图谱。

采用线程而非进程：任务是纯 I/O 等待，GIL 在网络阻塞时会释放，线程足够且无需序列化跨进程数据。

### 1.6 并发数配置

沿用项目里已有的 `BAILIAN_L2_FLOW_MAX_CONCURRENCY` 写法：

```python
DEFAULT_BRANCH_MAX_CONCURRENCY = 4

def staged_branch_concurrency(pending_branches: int) -> int:
    """并行扩展一级分支时的最大并发数；<=0 表示所有分支一次性并发。"""
    configured = _env_int("BAILIAN_STAGED_BRANCH_MAX_CONCURRENCY", DEFAULT_BRANCH_MAX_CONCURRENCY)
    if configured <= 0:
        return max(1, pending_branches)
    return max(1, min(configured, pending_branches))
```

设为 `1` 即退回串行，便于对照调试。

### 1.7 顺带修掉的 `.env` 加载时序问题

`_env_int()` 原来直接 `os.getenv`，而 `os.environ` 只在 `load_bailian_env()`（内部调 `load_dotenv`）执行后才会有 `.env` 的内容。

分支阶段读配置的时机在**任何一次百炼调用之前**，于是：

- 跑 `--stage all`：骨架阶段先调过百炼，`.env` 已加载 → 配置读得到；
- 跑 `--stage branches`：没人加载过 `.env` → `BAILIAN_STAGED_BRANCH_LIMIT` 和并发参数**静默失效**，退回默认值。

修法是一行，与 `l2_flow_relations._configured_int` 的做法一致：

```python
def _env_int(name: str, default: int) -> int:
    # 分支阶段可能在任何一次百炼调用之前就读取配置，这里自己确保 .env 已加载。
    load_bailian_env()
    value = os.getenv(name)
    ...
```

`load_dotenv(override=False)`，所以优先级仍是 **shell 环境变量 > `.env` 文件 > 代码默认值**。

### 1.8 验证

用 mock 掉百炼调用的脚本跑过：5 个分支、第 3 个故意抛错、每次调用 `sleep(0.5)`。

```
peak_concurrency=4   elapsed=1.02s   merged_nodes=42
```

- 峰值并发 4，上限生效；
- 耗时 1.02s，串行需约 2.5s；
- 记录顺序 `t_001..t_005` 与骨架一致；
- `staged_errors.json` 只含 `t_003`；
- 合并节点数 1 + 5 + 4×9 = 42 正确。

验证脚本是一次性的，未入库。

### 1.9 注意事项

- 并发时日志会交叉输出，每行都带分支名，另有 `分支进度 N/M` 汇总。
- 并发 4 意味着同时有 4 路 `web_search` 打到百炼。若遇到限流（429），调小该值。
- `BAILIAN_STAGED_BRANCH_LIMIT` 与并发参数正交：前者决定**跑多少个**分支（会让图缺分支，仅调试用），后者决定**跑多快**（不影响结果）。

## 二、上市公司过滤

### 2.1 设计原则：一份数据 + 一个开关

公司挂载关系（哪家公司挂哪个节点、理由、置信度）在 agent 阶段一次性全量算好，落在 `company_attachments.json` 里，**包含上市与非上市公司**。

"只要上市公司"不是另一套挂载流程，而是在这份结果上做的一次过滤。这样切换范围不需要重跑任何 LLM 调用。

### 2.2 判定口径（核心）

判定函数在 [`company_attachments.py:483`](../tools/agent/company_attachments.py)：

```python
def is_listed_company(company: dict[str, Any]) -> bool:
    return company.get("is_listed") is True or company.get("is_abroad_listed") is True
```

字段来自源 CSV 的 `islisted` / `isabroadlisted` 两列。

**关键判断：`islisted` 空白表示"非上市"，而不是"数据缺失"。** 申万全量分类结果 CSV 里约一半的行该列为空，但上市主体自己那行一定带 `islisted=1`；留空的是集团母公司和子公司（华为投资控股、茅台集团、中芯国际(上海) 等）。因此只认显式标记，空值一律判为非上市。

境外上市单独用 `is_abroad_listed` 兜住——少数公司只有这一个标记。所以"仅上市"的实际含义是 **A股上市 + 境外上市**。

### 2.3 单一过滤实现

`filter_listed_attachments()`（[`company_attachments.py:495`](../tools/agent/company_attachments.py)）是唯一的过滤入口，返回「过滤后的 payload + 统计块」。它的几个要点：

- **级联删除**：删掉非上市公司后，引用它们的挂载记录一并删除；
- **反向清理**：过滤后没有任何挂载记录的公司也删掉，与 `build_payload` 组装公司列表的口径保持一致；
- **元数据原样保留**：`schema_version` / `industry_id` / `graph_fingerprint` / `candidate_source` / `scope` 全部透传，因此过滤后的 payload 仍能通过 `attachment_file_status` 校验，不必重跑挂载 agent；
- **不修改入参**，且**幂等**（过滤两次结果相同）；
- 附带 `listed_filter` 块，记录规则、时间和前后数量，便于追溯。

统计块包含 `company_count_before/after`、`attachment_removed`、`listed_domestic_count`、`listed_abroad_only_count`、`removed_flag_counts`（区分 `is_listed=false` 与 `is_listed=null`）。

### 2.4 三条消费路径

同一个过滤函数被三处复用，保证口径不会分叉：

**① 后端 API** —— [`backend/app/main.py:180`](../backend/app/main.py)

```python
    listed_only: bool = Query(default=False),
    ...
    if listed_only:
        payload, _ = filter_listed_attachments(payload)
    items = aggregate_node_companies(graph, payload, node_id, include_descendants=include_descendants)
```

即 `GET /api/nodes/{id}/companies?...&listed_only=true`。默认 `false`，即 API 层面默认全量。

**② CSV 导出** —— [`export_csv.py:127`](../tools/agent/export_csv.py)

`export_company_attachment_csv()` 新增 `listed_only: bool = True`，**默认只导出上市公司**（与 API 默认值相反，因为交付 CSV 的场景就是要上市公司）。命令行用 `--include-unlisted` 才导出全部：

```bash
python tools/agent/export_csv.py --industry-id food_beverage --include-unlisted
```

过滤发生时会打日志：`[agent] CSV 仅导出上市公司：公司 5 → 3，挂载 5 → 3。`

**③ 前端离线包** —— 离线 HTML 没有后端，前端自己过滤，因此在 [`api.ts:58`](../frontend/src/api.ts) 有一份等价实现：

```ts
/**
 * Mirror of `is_listed_company` in tools/agent/company_attachments.py — keep the
 * two in sync. ...
 */
export function isListedCompany(company: { is_listed?: boolean | null; is_abroad_listed?: boolean | null }) {
  return company.is_listed === true || company.is_abroad_listed === true;
}
```

> ⚠️ 这是全项目唯一一处判定逻辑的重复。改判定规则时两边必须同步，注释里已互相标注。

### 2.5 前端交互

**状态**：`CompanyScope = "listed" | "all"`，默认 `listed`（[`App.tsx:17`](../frontend/src/App.tsx) 与 `:140`）。

**入口**：筛选栏中的「公司范围」二选一按钮——"仅上市" / "全部"。

**取数**：展开节点公司时把开关翻译成请求参数（`App.tsx:559`）：

```tsx
const response = await fetchNodeCompanies(industryId, nodeId, 500, 0, false, companyScope === "listed");
//                                                        includeDescendants=false ↑    ↑ listedOnly
```

`includeDescendants=false` —— 画布上只挂**直接挂载**到该节点的公司。

`fetchNodeCompanies`（[`api.ts:143`](../frontend/src/api.ts)）分两路：在线拼 `listed_only` query 交给后端；离线在内存里 `filter(c => !listedOnly || isListedCompany(c))`。

**切换时必须清缓存**（`App.tsx:573`）：

```tsx
setCompanyScope(scope);
// Cached responses were fetched under the previous scope, so drop them and
// refetch whatever is currently expanded on the canvas.
setCompanyResponses({});
setSelectedCompany(null);
const responses = await Promise.all(
  expanded.map((nodeId) => fetchNodeCompanies(industryId, nodeId, 500, 0, false, scope === "listed"))
);
```

原因：`companyResponses` 按 nodeId 缓存，缓存键里**不含 scope**。不清就会把旧范围的结果显示在新范围下。

**画布呈现**：公司被合成图节点，ID 加 `company:` 前缀避免与产业链节点撞号，绿色 `#16a34a` 小圆点，边标签为"公司"。点击时靠前缀分流到公司详情面板。

**详情面板**的上市标记是三态显示（`App.tsx:1022`）：

```tsx
{selectedCompany.is_listed !== null && selectedCompany.is_listed !== undefined &&
  <span>{selectedCompany.is_listed ? "上市" : "非上市"}</span>}
```

字段缺失时整个标签不渲染，避免把"不知道"显示成"非上市"。

## 三、配置速查

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `BAILIAN_STAGED_BRANCH_MAX_CONCURRENCY` | 4 | 分支并行最大并发；0 = 全部一次性并发，1 = 串行 |
| `BAILIAN_STAGED_BRANCH_LIMIT` | 0 | 只扩展前 N 个 L1，**仅调试用**；0 = 全部 |

两者都读 `backend/.env`，也可用命令行前缀临时覆盖：

```bash
BAILIAN_STAGED_BRANCH_MAX_CONCURRENCY=8 python tools/agent/build_candidate_graph.py --industry-id food_beverage --stage branches
```

| 接口 / 参数 | 默认 | 含义 |
|---|---|---|
| `GET /api/nodes/{id}/companies?listed_only=` | `false` | API 默认返回全量公司 |
| `export_company_attachment_csv(..., listed_only=)` | `True` | CSV 默认只导出上市公司 |
| `export_csv.py --include-unlisted` | 关 | 开启后 CSV 导出全部公司 |
| 前端「公司范围」 | 仅上市 | 画布展开时的默认范围 |

注意三处默认值并不一致，是刻意的：API 保持中立，CSV 面向交付所以默认上市，前端面向投研浏览所以默认上市。

## 四、遗留事项

1. **判定逻辑双份实现**（Python + TypeScript），依赖注释约束同步，没有自动校验机制。
2. **`_env_int` 的静默容错**：值写成 `4.0` 或 `abc` 时 `int()` 抛 `ValueError` 被 `except` 吞掉，静默退回默认值，没有任何提示。写配置时须确保是整数。
3. **前端公司缓存键不含 scope**，因此切换范围只能整体清空重取；若将来公司量级变大，可考虑把 scope 并入缓存键以避免重复请求。
