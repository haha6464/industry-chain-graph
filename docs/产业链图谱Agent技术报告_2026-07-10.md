# 产业链图谱 Agent 技术报告

报告日期：2026-07-10

## 1. 项目背景

本项目面向华泰证券基础行业研究场景，目标是构建一套产业链图谱构建、维护和展示系统。当前系统包含两条主线：

1. 图谱应用  
   提供产业链图谱展示、筛选、节点审计、Agent 工作流触发、产物查看和 CSV 导出能力。

2. 构建 Agent  
   调用阿里云百炼 Qwen Responses API，分阶段完成行业产业链图谱构建、质量评估、硬规则校验和格式修复。

项目当前的核心目标不是单次生成一张图，而是形成一套可复用、可审计、可逐步批量化的产业链图谱生产流程。每个行业最终交付物包括：

- `graph.json`：正式产业链图谱；
- 节点 CSV；
- 关系 CSV；
- 构建和校验过程中的中间产物。

## 2. 技术架构

### 2.1 总体架构

系统采用前后端分离架构，后端负责图谱数据读取、Agent 子进程调度、产物管理和 Neo4j 导入；前端负责图谱可视化、行业切换、筛选、节点审计和 Agent 工作流操作。

```text
React + Vite 前端
  -> FastAPI 后端 API
    -> data/industries/{industry_id}/graph.json
    -> Agent CLI 子进程
    -> Neo4j Repository（可选）
    -> CSV 导出工具
```

当前 Neo4j 不是前置依赖。图谱展示默认直接读取 `graph.json`，Neo4j 主要用于本地调试、图数据库查询和后续扩展。

### 2.2 后端技术栈

后端位于 `backend/app/`，主要技术栈如下：

- FastAPI：提供 HTTP API；
- Pydantic：定义请求和响应模型；
- pydantic-settings：读取 `backend/.env` 配置；
- Neo4j Python Driver：封装图数据库连接；
- Python 子进程：调用 Agent CLI 工具；
- 本地 JSON/JSONL 文件：存储图谱、候选图谱、证据和中间产物。

主要模块职责：

- `main.py`  
  定义所有 API 路由，包括行业列表、图谱读取、Agent 构建、增量更新、产物查看、CSV 导出和 Neo4j 导入。

- `schemas.py`  
  定义 Pydantic 数据模型，是前后端字段契约的后端权威来源。

- `graph_loader.py`  
  从 `data/industries/{industry_id}/graph.json` 加载图谱，并支持关键词、层级、关系类型、产业链位置等筛选。

- `agent_service.py`  
  负责 Agent 子进程调度、运行状态维护、日志收集、产物路径管理和运行报告读取。运行状态保存在内存字典 `RUNS` 中，后端重启后会丢失。

- `repository.py`  
  封装 Neo4j 读写逻辑，包括导入图谱和 Cypher 查询。

- `neo4j_client.py`  
  封装 Neo4j 驱动连接管理。

- `ai_service.py`  
  图谱问答服务，使用 OpenAI 兼容 API，根据图谱上下文回答问题。

### 2.3 前端技术栈

前端位于 `frontend/src/`，主要技术栈如下：

- React 18；
- Vite；
- TypeScript；
- 浏览器端图谱展示和交互组件；
- 后端 API 封装。

主要文件职责：

- `App.tsx`  
  主页面入口，包含图谱展示页和 Agent 工作流页。前端支持行业选择、图谱筛选、节点审计、运行 Agent、查看日志和查看产物。

- `api.ts`  
  封装后端 API 调用，包括行业列表、图谱读取、Agent 构建、增量更新、候选图谱应用、CSV 导出等。

- `types.ts`  
  TypeScript 类型定义，需要与 `backend/app/schemas.py` 保持一致。

前端当前已支持将构建流程拆成多个操作入口：

- 搜索规划；
- 一级骨架构建；
- 分支扩展与评估；
- 最终校验；
- 增量更新；
- CSV 导出；
- Agent 产物查看。

### 2.4 Neo4j 实现

Neo4j 通过 `docker-compose.yml` 启动，作为本地可选图数据库。当前系统中，Neo4j 的定位是辅助调试和后续图查询能力扩展，而不是图谱展示的强依赖。

图谱导入逻辑位于：

```text
backend/app/repository.py
backend/app/neo4j_client.py
```

当前图谱数据的权威来源仍是本地 `graph.json`。导入 Neo4j 时，会将节点和关系写入图数据库，便于后续使用 Cypher 查询上下游、父子层级和邻居节点。

这种设计有两个好处：

- 前端展示不依赖本地 Neo4j 是否启动，降低 demo 和调试门槛；
- 后续需要复杂图查询时，可以继续扩展 Neo4j 查询接口。

## 3. 数据模型与文件组织

### 3.1 图谱数据模型

图谱顶层结构为：

```json
{
  "industry": "食品饮料",
  "version": "v0.2-staged-build",
  "schema_version": "standard_industry_graph_v0.2_agent",
  "generated_at": "2026-06-26T...",
  "scope": "标清产业链图谱；不包含公司节点、股票代码、财务指标。",
  "source_basis": [],
  "nodes": [],
  "edges": []
}
```

节点核心字段包括：

- `id`：节点唯一 ID；
- `name`：节点名称；
- `node_type`：产业链、产业链环节或细分环节；
- `level`：数字层级；
- `chain_position`：root/upstream/midstream/downstream/support；
- `parent_id`：父节点；
- `description` / `business_description`：业务描述；
- `source_urls`：来源 URL；
- `confidence`：置信度。

关系核心字段包括：

- `source`：起点节点；
- `target`：终点节点；
- `relation_type`：只允许 `contains` 或 `upstream_downstream`；
- `relation_weight`：关系权重；
- `description`：关系说明；
- `source_urls`：来源 URL；
- `confidence`：置信度。

内部关系方向约定：

- `contains`：父节点 -> 子节点；
- `upstream_downstream`：上游节点 -> 下游节点。

### 3.2 数据目录

行业数据统一存放在：

```text
data/industries/
  manifest.json
  {industry_id}/
    graph.json
    candidate_graph.json
    sources.jsonl
    exports/
```

`manifest.json` 记录 25 个基础行业的行业 ID、行业名称、板块、状态、图谱路径和节点/关系数量。

当前只有 `food_beverage` 有完整 demo 图谱，其余行业仍处于 `pending` 状态。

### 3.3 CSV 导出

CSV 导出逻辑位于：

```text
tools/agent/export_csv.py
```

导出 mentor 格式时，关系类型和方向会转换：

| 内部关系 | 内部方向 | CSV 关系 | CSV 方向 |
|---|---|---|---|
| `contains` | 父 -> 子 | `SUBORDINATE_TO` | 子 -> 父 |
| `upstream_downstream` | 上游 -> 下游 | `DOWNSTREAM_OF` | 下游 -> 上游 |

节点 CSV 字段：

```text
节点id,节点类型,节点名称,节点标签,节点行业,业务描述,关键节点,产业链环节
```

关系 CSV 字段：

```text
起点节点id,起点节点名称,终点节点id,终点节点名称,关系类型,关系权重,关系描述
```

## 4. Agent 构建实现

### 4.1 Agent 工具链

Agent 工具位于 `tools/agent/`，既可以由后端子进程调用，也可以通过命令行独立运行。

核心入口包括：

- `build_candidate_graph.py`  
  候选图谱构建入口，支持 skeleton、branches、all 等阶段。

- `final_validate_graph.py`  
  最终硬规则校验入口，必要时调用百炼做格式修复。

- `update_graph.py`  
  增量更新入口。

- `common.py`  
  路径常量、JSON/JSONL IO、`standardize_graph()` 等公共逻辑。

- `bailian_client.py`  
  百炼 Qwen Responses API 封装，统一读取 `backend/.env` 中的百炼配置。

### 4.2 分阶段构建流程

当前默认构建策略是 staged，而不是一次性生成整张图。

流程如下：

```text
1. 生成搜索计划
2. 百炼联网搜索构建一级骨架
3. 评估一级骨架质量
4. 逐个扩展一级分支
5. 逐分支评估质量
6. 合并图谱和质量意见
7. 标准化为候选图谱
8. 执行硬规则校验
9. 必要时调用格式修复
10. 生成候选图谱、校验报告、复核队列和 CSV
```

这一设计解决了早期一次性生成整图时的几个问题：

- 请求范围过大，模型容易遗漏关键分支；
- 图谱深度和广度难以同时控制；
- 出错后不容易定位是哪一部分的问题；
- 整图重跑成本较高。

分阶段后，一级骨架和每个分支都可以独立评估和修正，便于把问题限制在局部。

### 4.3 Prompt 口径

当前构建 Prompt 的核心口径是“投研产业链节点”：

- 节点应是稳定产业分类单元；
- 节点应能服务于行业比较、成本拆解、上下游传导和公司业务归因；
- 优先抽取原材料、关键材料、零部件、系统、设备、工艺、产品、应用场景、渠道、物流、检测认证等节点；
- 不抽取公司、股票、财务指标、新闻事件、政策标题、市场趋势、平台能力、泛咨询服务等概念；
- 同一父节点下兄弟节点粒度要一致。

这套口径目前已经体现在：

```text
tools/agent/search/staged_bailian_builder.py
tools/agent/evaluators/bailian_quality_evaluator.py
tools/agent/search/bailian_responses_agent.py
```

### 4.4 标准化与校验

所有写入图谱的数据都必须经过：

```text
tools/agent/common.py::standardize_graph()
```

该函数负责补全节点和关系字段、生成默认类型、设置 `chain_segment`、补充默认来源、生成 edge ID 等。

硬规则校验位于：

```text
tools/agent/validators/graph_validator.py
```

主要检查：

- schema 是否符合要求；
- 节点 ID 是否重复；
- 节点名称是否重复；
- 是否存在公司字段；
- 关系类型是否合法；
- `contains` 和 `upstream_downstream` 是否冲突；
- 是否存在孤立节点；
- 来源 URL 是否缺失；
- 置信度是否低于阈值；
- 节点数量和 level=1 覆盖是否满足最低要求。

## 5. 后端 API 实现

当前后端 API 覆盖三类能力。

### 5.1 图谱应用 API

包括：

- `GET /api/health`
- `GET /api/industries`
- `GET /api/graph`
- `GET /api/nodes/{node_id}/neighbors`
- `POST /api/ask`

其中 `/api/graph` 支持按关键词、产业链位置、关系类型、层级等条件筛选图谱。

### 5.2 Agent 工作流 API

包括：

- `POST /api/agent/search-plan`
- `POST /api/agent/build-skeleton`
- `POST /api/agent/build-branches`
- `POST /api/agent/final-validate`
- `POST /api/agent/update`
- `GET /api/agent/runs/{run_id}`
- `POST /api/agent/runs/{run_id}/cancel`
- `GET /api/agent/runs/{run_id}/report`

后端通过子进程运行 Agent 脚本，并将运行状态、日志和步骤保存在内存中。前端通过轮询 run id 获取进度。

### 5.3 产物和导出 API

- `POST /api/industries/{id}/apply-candidate`

Agent 产物名称在 `backend/app/agent_service.py` 中集中注册，前端通过统一接口查看中间产物。

## 6. 增量更新与节点命名实验

### 6.1 问题

mentor 侧在做增量更新时，会从新闻文本中抽取可能的新节点。实验样例显示，很多抽取结果其实是事件句或指标变化，不是产业链节点，例如：

- 公司收入占比提升；
- 订单增长；
- 市占率提升；
- 估值承压；
- 竞争格局变化；
- 产能利用率提升。

如果直接把这些文本转成节点，会污染产业链图谱。如果简单禁止事件和指标，模型又会把“动力电池热管理系统集成商订单需求提升”这类本可匹配产业节点的文本错误丢弃。

### 6.2 实验脚本

本阶段新增了临时测试脚本：

```text
tools/agent/test_node_naming_prompt.py
```

脚本功能：

- 读取 `test_node.xlsx` 中前 10 条 `event_id/node_name`；
- 内置一组候选产业链节点；
- 调用现有百炼配置；
- 输出结构化判断结果；
- 保存 Prompt 和结果到 `data/` 下。

生成产物：

```text
data/node_naming_test_prompt.txt
data/node_naming_test_result.json
```

运行方式：

```powershell
.\scripts\run-agent.ps1 tools\agent\test_node_naming_prompt.py
```

### 6.3 实验结论

实验后得到的关键结论是：

```text
先剥离事件词和指标词，再抽取稳定产业对象，最后匹配候选节点或生成新节点。
```

示例结果：

- “电机零部件行业竞争格局重塑” -> 匹配“电机零部件”；
- “动力电池热管理系统集成商订单需求提升” -> 匹配“动力电池热管理系统”；
- “航盛电子车机系统订单增长” -> 匹配“车机系统”；
- “广和通并表收入规模提升” -> 不新增节点；
- “德赛西威/华阳集团等估值承压” -> 不新增节点；
- “同类定转子供应商市场份额下降” -> 进入复核。

因此，面向 mentor 侧的 Prompt 不宜设计成复杂批处理长 Prompt，而应作为单条 `node_target` 的命名规则嵌入原流程。

## 8. 当前不足

当前系统已经具备完整链路，但还有几个关键不足：

1. 图谱质量仍依赖人工融合  
   Agent 可以生成可复核的候选图谱，但高质量节点合并、粒度调整、同义归并和分支均衡仍需要人工判断。

2. 多行业稳定性仍需验证  
   食品饮料 demo 链路较完整，但其他 24 个行业尚未批量验证。不同产业的分支结构差异较大，Prompt 和规则还需要多行业试跑。

3. 增量更新仍处于早期阶段  
   当前已有基础更新链路，但对新闻文本到产业节点的识别、已有节点匹配、新节点生成、复核动作拆分仍需继续优化。

4. 前端复核能力不足  
   当前已有产物查看和复核队列基础，但还缺少接受、拒绝、改名、合并、移动父节点、废弃等操作界面。

## 9. 后续方向

后续方向这里只列出需要继续推进的问题，不展开具体方案：

- 公司主体节点：在标准产业链节点之外，增加公司主体与产业链节点的关联，并支持公司业务向上游产业环节聚合；
- 增量更新优化：提升新闻文本到产业链节点的门禁、匹配、复核和更新 diff 能力；
- 自动图谱融合：把当前依赖人工和 Codex 协助的节点合并、上收、改名、去重经验沉淀为项目自身规则；
- 质量评分体系：建立结构分和语义分，用于判断候选图谱是否达到交付标准；
- 多行业批量构建：在 25 个基础行业上验证构建流程稳定性和 Prompt 泛化能力；
- 前端复核闭环：支持人工确认结果回写，并将复核意见沉淀为规则。

## 10. 总结

当前项目已经形成了较完整的产业链图谱 Agent 技术框架：前端用于图谱展示和工作流操作，FastAPI 后端负责 API、产物管理和 Agent 调度，Agent CLI 负责百炼调用、分阶段构建、质量评估、硬规则校验和 CSV 导出，Neo4j 作为可选图数据库用于调试和后续扩展。

本阶段的主要技术进展是将图谱构建从一次性生成改为分阶段构建和评估，并通过增量更新节点命名实验明确了“先剥离事件/指标，再抽取稳定产业对象”的 Prompt 规则。

下一步的重点是减少对人工融合和 Codex 协助的依赖，让项目自身逐步具备稳定生成高质量产业链图谱的能力。
